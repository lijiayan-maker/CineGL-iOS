# 原理与设计取舍

简体中文 | [English](design-notes.md)

> 这篇是写给「想搞懂这个相机的 GPU 到底在忙什么」的人，包括三个月后忘光了的我自己。
> 管线本身的原理（Log、3D LUT、Dual Kawase、颗粒……）在 Android 版那篇里讲过一遍了，这里不炒冷饭，
> 重点聊**把它搬到 iOS 时换了什么、为什么换、踩了哪些坑**。使用方法、构建命令请看 [README](../README.md)。

## 先说结论：同一条管线，换了一副发动机

我给自己定的规矩没变：**每一个 pass 都要能对应到一台真实胶片相机里的某个东西**。

```
真实世界                     CineGL（iOS）里
────────                     ───────────────
镜头    畸变、色散、暗角   →  input pass（CINInput.metal）
胶片曝光 高光散射成光晕    →  glow pass（Dual Kawase 金字塔）
冲洗    显影出颜色         →  film pass 里的 3D LUT
银盐    颗粒               →  film pass 里的噪声
放映    看片子             →  present pass（还顺手画了斑马纹、峰值、波形图）
```

pass 的划分、每个 pass 的参数、每一行色彩数学，都和 Android 版一一对应——我甚至把 Android 的 C++ 单测逐条搬成了 XCTest，数字一个没改。两边对得上，以后哪边出了怪事，拿另一边当对照组就行。

变的是底下那一层：**OpenGL ES 换成了 Metal，C++ 换成了 C + simd，Kotlin + Compose 换成了 Objective-C + UIKit**。

---

## 为什么不继续用 OpenGL ES

最省事的方案明明摆在那儿：iOS 也有 OpenGL ES，GLSL 抄过来就能跑，两边还能共用一份着色器。我没选它，理由就一条：**性能是唯一的指标**。

- Apple 从 iOS 12 起就把 OpenGL ES 标成了弃用。它现在还能跑，靠的是一层翻译到 Metal 的兼容层——绕一圈再到 GPU，等于高速公路上走辅路。
- Metal 有一样 GLES 在 iOS 上没有的宝贝：`CVMetalTextureCache`。相机给的 `CVPixelBuffer` 底下是 IOSurface，直接「借」成 Metal 纹理，一个字节都不拷。录像也一样：GPU 直接画进写入器的像素缓冲。
- 半精度渲染目标（光晕金字塔要用）在 Metal 上是「标配」，不用像 Android 那样先查 `EXT_color_buffer_half_float`、查不到再退回 RGBA8。
- 着色器在**编译期**就编成 `default.metallib`。Android 那篇里提过唯一一个活到手机上的 bug——光晕的纹理和强度都叫 `uHalation`——在这里根本活不过 ⌘B。

代价是着色器得一个个重写成 MSL。好在 GLSL 和 MSL 是表兄弟，`vec3` 改 `float3`、`texture()` 改 `.sample()`、`mix(lo, hi, step())` 改 `select()`，体力活而已。真正费脑子的是下面这个。

---

## 坐标系：这次多了一个翻转

Android 那篇说「坐标系是踩坑重灾区」，到了 Metal 这个坑又挖深了一铲：**Metal 的纹理原点在左上角**，GL 在左下角。

我的选择是「核心不动，边界上翻」：

- 所有矩阵、所有 uv 照旧按 GL 习惯（左下原点、v 向上），`CINFrameGeometry` 里的数学和 Android 版逐字一致，单测也逐字一致；
- 着色器里采样「管线自己画出来的纹理」时，统一过一道 `tc(uv) = (u, 1 - v)`；
- 相机缓冲、照片位图本来就是「第 0 行在最上面」，用的是图像坐标，不翻。

意外之喜：Metal 的渲染目标读回来本来就是「顶行在前」，所以 Android 拍照时为了对付 `glReadPixels` 加的 `flipY`、缩略图图集的 `kFlipV`，在 iOS 上统统用不着。翻转从三处变成一处，心里踏实多了。

### 没有 SurfaceTexture 的神秘矩阵

Android 上相机画面进 `SurfaceTexture`，系统顺手给一个变换矩阵，把传感器的旋转、镜像都算好了。iOS 没这待遇：`AVCaptureVideoDataOutput` 给的缓冲是**传感器原生方向**（横着的，要顺时针转 90° 才正），前置也不镜像。

当然可以让 AVFoundation 帮忙转（设 `videoRotationAngle = 90`），但那是实打实地把每一帧整张旋转一遍——又是性能。所以缓冲保持原样，旋转和镜像交给 GPU：反正 input pass 本来就要按矩阵采样，多乘一个矩阵不要钱。

更巧的是，这个矩阵 Android 版里已经有了——`stillInputMatrix`，当初是给拍照用的（JPEG 也是传感器方向）。到了 iOS，**预览和拍照用的是同一个矩阵**，一鱼两吃。

## 相机缓冲：要 YCbCr，不要 BGRA

让 `AVCaptureVideoDataOutput` 直接吐 BGRA 是最省心的：着色器里拿来就用。但相机内部是 YUV，系统得先帮你转一遍——又是一整帧的搬运。

我要的是 `420f`（8 bit YCbCr 双平面），亮度、色度各借成一张纹理（`R8` + `RG8`），在 input pass 里自己乘矩阵转 RGB。这和 Android 上 `samplerExternalOES` 在采样时「偷偷」做 YUV → RGB 是一个道理，只不过这次是我亲手做的：

- 矩阵按缓冲附件挑：BT.709 / 601 / 2020；
- 全范围（0–255）和视频范围（16–235）各一套偏移；
- Apple Log 用的是 10 bit 的 `x420`，数据放在 16 bit 的高 10 位，采样出来是 `v16 / 65535`，换算时要多乘一个 `65535 / 64 / 1023`——差了这一下，黑位会偏一丢丢，肉眼看不出来，单测看得出来。

拍照那边倒反过来了：我直接问 `AVCapturePhotoOutput` 要**未压缩的 BGRA**。Android 只能拿 JPEG 再解码，等于先把照片压成饼干再泡开；iOS 给得了原料，何必多此一举。

## Log：ISP 曲线变成了 Apple Log

Android 的第三档 Log 是把 CineLog 采样成 64 个点塞给 ISP（`TONEMAP_CURVE`）。iOS 没有这个口子，但有更正宗的：iPhone 15 Pro 起的 **Apple Log**——相机直出 10 bit Log，还是 Rec.2020 原色。

我没有让 Apple Log 直通到底，而是在 input pass 里**先解码成线性 Rec.709，再编码成 CineLog**。这样后面的光晕、LUT、颗粒完全不用管信号是从哪来的：管线内部永远只有 Rec.709 和 CineLog 两种编码，和 Android 一样。Apple Log 只是多了一个「入口」，像机场多开了一条安检通道，进去以后都是同一个候机厅。

它的曲线是分段的（暗部一段抛物线、往上是对数），参数照 Apple 的白皮书抄进 `CINColor.m` 和着色器两份，单测验证拼接点连续、编解码互逆、18% 灰落在 0.488。

## 手动参数：iOS 给了什么、没给什么

**曝光**：和 Camera2 一样，iOS 也只有「全自动」和「全手动（custom）」两档，没有快门优先 / 感光度优先。半自动的思路原封不动：自动时记下 `ISO × 曝光时间`，锁一个、算另一个。连单测的数字都是同一组。

**白平衡**：这里 iOS 比 Android 大方——它能把「色温 + 色调」直接换算成设备增益。于是支持自定义增益的设备上，色温是**绝对值**：从自动白平衡当前的色温起步，切到手动那一下画面不跳。Android 只能「相对 AWB 偏移」，为了不跳，只好把 5500K 设成「什么都不变」。不支持自定义增益的（比如部分前置），就退回和 Android 一样的做法：锁住 AWB，在 GPU 里乘增益。

**对焦**：iOS 只给镜头位置 0–1，不告诉你是几米。我按薄透镜近似「镜片移动量 ∝ 1 / 物距」，把它线性换算成屈光度，刻度盘上照样显示「0.50m」。不精确，但单调、手感对——和 Android 那篇说白平衡斜率时一个态度。

**多摄**：后置的「三摄 / 双摄」虚拟设备能在广角、长焦之间无缝切换，可它往往不让你锁镜头位置。手动对焦和变焦档位只能二选一的时候，我选手动：**这个 App 的核心是手动参数**。所以规则是「虚拟设备同时支持自定义曝光和锁镜头，才用它；否则用单个广角镜头」。

## 录像：AVAssetWriter 与主机时钟

Android 上 `MediaCodec` + `MediaMuxer` 那一大坨，在 iOS 上缩成了一个 `AVAssetWriter`。省下来的力气花在了两件事上。

**一是 GPU 跑完才能交货。** 录像帧是 GPU 画进像素缓冲的，命令提交了不等于画完了。最直觉的写法是在 `addCompletedHandler` 里 append——但 Metal 不保证这些回调的线程和先后，一旦乱序，写入器就会因为时间戳不递增把帧扔掉。我的做法是在一个串行队列里**按提交顺序**排队：每一帧先 `waitUntilCompleted`，再交给写入器。停止录像时也往这个队列里排一个「收工」，前面的帧全交完才算停稳。

**二是音画同一个时钟。** Android 那边要按相机时间戳的来源挑 `BOOTTIME` 还是 `MONOTONIC`；iOS 简单些，大家都换算到**主机时钟**：相机帧用输入端口的时钟换算，音频用 `AVAudioTime.hostTime`。写入器以第一帧视频为起点，比它早到的声音直接丢掉。

编码缓冲依旧永远横着，竖拍时在轨道上写旋转——和 Android 一样，理由也一样。

## 模拟器：自己造一台相机和一个麦克风

Android 模拟器至少还有个 3D 房间可以拍。iOS 模拟器呢？`AVCaptureDevice` 一个都没有，真正的家徒四壁。

不能拍就没法调界面、没法截图、手动参数更是无从谈起。于是我**自己造了一台相机**（`CINSimulatedCamera`）：

- 场景用 Core Graphics 画一次：木墙、窗户、色卡、显示器、绿植、台灯。另画一张「自发光」图，窗户和灯泡亮度乘上 6——比白还亮，过曝、光晕、斑马纹才有东西可看；
- 着色器按 `ISO × 快门` 线性缩放亮度、超过 1.0 的直接截掉，和真传感器一样会过曝；手动对焦用更高的 mip 级别模拟失焦；补光就是把正面提亮；
- 关键一步：**输出和真机一样的传感器方向缓冲**（横着、要顺时针转 90°）。这样模拟器上跑的是真机同一条路径，转正、裁切、点击对焦的坐标换算全都被测到了，而不是走一条「模拟器专用」的捷径。

麦克风则是被逼出来的。模拟器里 `AVAudioEngine.inputNode` 要经 coreaudiod 转到 Mac 的麦克风，第一次跑就卡在 RPC 上，几秒后系统直接 `abort`。更阴的是，它卡的是主线程：在被 abort 之前，界面上 ISO 一直显示「A 0」，我还以为是读数回调写错了，查了半天。教训：**界面不更新，先看主线程在干嘛**。最后模拟器上改用一路 −45 dBFS 的虚拟底噪，电平表照跳、录像照样有音轨。

## 界面：把 Compose 一比一搬到 UIKit

要求是「界面完全一样」，所以我没用 UIKit 自带的 `UISlider`、`UISwitch`——它们是 iOS 的长相，而 Android 版用的是 Material 3。滑杆（16pt 的轨道、4×44 的竖条滑块、6pt 空隙、末端一个小圆点）和开关（52×32、关时 16pt 灰点、开时 24pt 白点）都是照着 Compose 的尺寸手画的。其他控件的字号、间距、颜色，全部从 Compose 代码里抄数字，不靠截图目测。

踩了两个 UIKit 的坑，记下来防止再踩：

- **`viewWithTag:` 会先比较自己。** 分段控件里每个选项的 tag 是序号，选项里的文字标签 tag 是 1——于是第二个选项（tag 也是 1）调 `viewWithTag:1` 拿回来的是它自己，往一个按钮上 `setText:`，启动即崩溃。子视图的 tag 现在一律从 1001 起。
- **`UIScrollView` 默认不抢 `UIControl` 的触摸。** 设置面板里几乎每一行都是可点的开关行，手指一按上去，滚动视图就不动了。重写 `touchesShouldCancelInContentView:` 返回 YES 才和 Compose 的滚动容器一个手感；滑杆那边再用 `gestureRecognizerShouldBegin:` 把横向拖动留给自己。

还有一个从 Android 搬过来的老教训：刻度盘的拖动量要**在刻度盘内部累积**，不能每次都从外面传回来的值重算——曝光补偿取整到 1/3 档，慢慢拖时每次几个像素都被取整吃掉，就永远拖不动。

## 冷宫名单：想过但没做的

| 方案 | 为什么没做 |
|---|---|
| 继续用 OpenGL ES，和 Android 共用 GLSL | 已弃用、走兼容层；这个项目 iOS 端只看性能 |
| 把 Android 的 C++ 核心原样搬过来 | 两个仓库各自维护；这边的目标之一是练 Objective-C，C + simd 已经够用，而且 simd 类型和 MSL 是同一种 |
| `AVCaptureVideoPreviewLayer` 做预览 | 预览必须走自己的管线，否则影调、监看辅助都上不了屏 |
| `AVCaptureMovieFileOutput` 录像 | 它只录相机原始画面，录不了自己渲染的结果 |
| 让相机输出 BGRA | 系统要多转一遍，YCbCr 双平面在着色器里转是免费的 |
| 拍照拿 HEIC / JPEG 再解码 | 未压缩 BGRA 直接上 GPU，少一轮编解码 |
| Core Image 做滤镜 | 省事，但这是个学习项目，就是要自己写每一个 pass |
| ProRes Log 录制 | 需要写入 ProRes 编码器和更大的存储，先把 H.264 管线跑通 |
| 动态照片（实况） | 和 Android 一样：考的是编码和容器，不是 GPU |

## 练习题

Android 那篇的六道题在这里都能做（锐化、四面体插值、RGBA16F、直方图、GPU 测光、RGB 分量示波器），换成 Metal 的写法即可。再加几道 iOS 特色的：

1. **用 compute shader 做直方图**：Metal 的计算着色器 + 原子操作，比波形图那种「顶点着色器散点」更直接。对比两者的耗时。
2. **ProRes 422 HQ + Apple Log 录制**：把 `CINVideoRecorder` 的编码器换成 ProRes，LUT 烧录关闭时录出真正能进调色软件的素材。
3. **用 Metal System Trace 看一帧**：在 Instruments 里找出最贵的 pass，试着把光晕和柔光的金字塔合并成一条。
4. **真机上的 `CVMetalTextureCache`**：故意把 `keepAlive` 去掉，观察相机复用 IOSurface 时画面撕裂的样子——然后加回来。

做完这些，你对「相机里的 GPU 在忙什么」大概就比大部分人清楚了。至少，比三个月前的我清楚。
